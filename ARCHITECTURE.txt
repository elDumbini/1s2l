1. ОБЩАЯ АРХИТЕКТУРА И СЛОИ
================================================================================

Проект использует трёхслойную архитектуру (3-Layer Architecture):

┌─────────────────────────────────────────────────────────────────┐
│                    HTTP REQUEST (Express)                       │
└────────────────────────────┬────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│  СЛОЙ 1: CONTROLLER (Контроллер)                                │
│  Назначение: Обработка HTTP запросов и ответов                  │
│  Ответственность:                                               │
│    - Извлечение данных из req (params, query, body)             │
│    - Вызов сервисов                                             │
│    - Формирование HTTP ответов (status codes, headers)          │
│    - Передача ошибок в next() для глобального обработчика       │
│  НЕ ДЕЛАЕТ:                                                     │
│    - Бизнес-логику                                              │
│    - Валидацию данных (только HTTP валидация через middleware)  │
│    - Работу с БД                                                │
│    - Преобразование типов (Number(), String() и т.д.)           │
└────────────────────────────┬────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│  СЛОЙ 2: SERVICE (Сервис)                                       │
│  Назначение: Бизнес-логика приложения                           │
│  Ответственность:                                               │
│    - Применение дефолтных значений                              │
│    - Преобразование данных (например, SortDirection → MongoSort)│
│    - Валидация бизнес-правил (существует ли блог, пост и т.д.)  │
│    - Обработка ошибок и преобразование в доменные исключения    │
│    - Координация работы нескольких репозиториев                 │
│    - Транзакции и атомарные операции                            │
│    - Вычисления и бизнес-расчёты                                 │
│    - Агрегация данных из нескольких источников                  │
│    - Кэширование (при необходимости)                            │
│    - Логирование бизнес-событий                                 │
│    - Работа с внешними API и сервисами                           │
│    - Управление жизненным циклом сущностей                       │
│  НЕ ДЕЛАЕТ:                                                     │
│    - HTTP операции                                              │
│    - Прямую работу с БД                                         │
│    - Маппинг документов БД в доменные модели                    │
└────────────────────────────┬────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│  СЛОЙ 3: REPOSITORY (Репозиторий)                               │
│  Назначение: Работа с базой данных                               │
│  Ответственность:                                                │
│    - Выполнение запросов к БД (find, insert, update, delete)    │
│    - Маппинг документов БД (_id) в доменные модели (id)          │
│    - Преобразование типов БД (ObjectId → string)                 │
│    - Бросание исключений при ошибках БД                          │
│  НЕ ДЕЛАЕТ:                                                      │
│    - Бизнес-логику                                               │
│    - Применение дефолтных значений                                │
│    - Обработку ошибок (только бросает исключения)               │
│    - Валидацию данных                                            │
└────────────────────────────┬────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│                    MONGODB DATABASE                              │
└─────────────────────────────────────────────────────────────────┘

3. ТИПЫ ДАННЫХ И ИХ ХРАНЕНИЕ
================================================================================

3.1. ДОМЕННЫЕ ТИПЫ (Domain Types)
────────────────────────────────────────────────────────────────────────────
Место: src/{domain}/types/
Примеры: BlogItem, PostItem

Назначение:
  - Описывают сущности предметной области
  - Используются во всех слоях (Controller, Service, Repository)
  - Не зависят от БД или HTTP

Пример:
  // src/blogs/types/types.ts
  export type BlogItem = {
    id: string;              // Преобразован из _id MongoDB
    name: string;
    description: string;
    websiteUrl: string;
    createdAt: string;
    isMembership: boolean;
  };


3.2. DTO (Data Transfer Objects)
────────────────────────────────────────────────────────────────────────────
Место: src/{domain}/dto/
Примеры: CreateBlogDTO, GetBlogsDTO, UpdatePostDTO

Назначение:
  - Типы для передачи данных между слоями
  - Request DTO: данные, которые приходят в запросе (CreateBlogDTO)
  - Response DTO: данные, которые возвращаются в ответе (GetBlogsDTO)

Пример:
  // src/blogs/dto/blogs.dto.ts
  export type CreateBlogDTO = Pick<BlogItem, "name" | "description" | "websiteUrl">;
  export type GetBlogsDTO = PaginatedResponse<BlogItem>;


3.3. QUERY TYPES (Типы запросов)
────────────────────────────────────────────────────────────────────────────
Место: src/{domain}/types/
Примеры: GetBlogsQuery, GetPostsQuery

Назначение:
  - Типы для query параметров HTTP запросов
  - Расширяют PaginationQuery из core/types/common.types.ts
  - Используются в контроллерах для типизации req.query

Пример:
  // src/blogs/types/types.ts
  import { PaginationQuery } from "../../core/types/common.types";
  
  export type GetBlogsQuery = PaginationQuery & {
    searchNameTerm?: string;  // Дополнительный параметр для блогов
  };


3.4. ОБЩИЕ ТИПЫ (Common Types)
────────────────────────────────────────────────────────────────────────────
Место: src/core/types/
Файлы:
  - types.ts: HTTP статусы, ClientError, ROUTES
  - common.types.ts: PaginationQuery, PaginatedResponse, MongoSortDirection

Назначение:
  - Типы, используемые в нескольких доменных областях
  - Базовые типы для пагинации, сортировки
  - Утилиты для преобразования типов

Пример:
  // src/core/types/common.types.ts
  export type PaginationQuery = {
    pageNumber?: number;
    pageSize?: number;
    sortBy?: string;
    sortDirection?: SortDirection;
  };
  
  export type PaginatedResponse<T> = {
    items: T[];
    totalCount: number;
    pagesCount: number;
    page: number;
    pageSize: number;
  };


3.5. ТИПЫ ДОКУМЕНТОВ БД (Database Document Types)
────────────────────────────────────────────────────────────────────────────
Место: src/db/mongodb.ts и src/{domain}/repositories/

Назначение:
  - Внутренние типы для работы с MongoDB
  - Используются только в репозиториях
  - Имеют поле _id (ObjectId) вместо id (string)

Пример:
  // src/db/mongodb.ts
  type BlogDocument = Document & {
    name: string;
    description: string;
    websiteUrl: string;
    createdAt: string;
    isMembership: boolean;
  };


ИЕРАРХИЯ ТИПОВ:
  core/types/common.types.ts (базовые типы)
         ↓
  {domain}/types/ (расширяют базовые, добавляют доменные)
         ↓
  {domain}/dto/ (используют доменные типы для DTO)
         ↓
  Используются в Controller → Service → Repository

4. ПОТОК ДАННЫХ ЧЕРЕЗ СЛОИ
================================================================================

ПРИМЕР: GET /blogs?pageNumber=1&pageSize=10&searchNameTerm=test

1. HTTP REQUEST
   ────────────────────────────────────────────────────────────────────────
   Express получает запрос и направляет в роутер

2. ROUTER (blogs.router.ts)
   ────────────────────────────────────────────────────────────────────────
   - Применяет middleware: paginationAndSortingValidation, errorValidationMiddleware
   - Направляет в контроллер: blogsController.getBlogs

3. CONTROLLER (blogs.controller.ts)
   ────────────────────────────────────────────────────────────────────────
   Входные данные:
     req.query = {
       pageNumber: "1",        // строка из URL
       pageSize: "10",          // строка из URL
       searchNameTerm: "test"   // строка из URL
     }
   
   Действия:
     - Извлекает данные из req.query (уже валидированные middleware)
     - Вызывает сервис: blogsService.getBlogs(req.query)
     - Получает результат и отправляет HTTP ответ
   
   Код:
     const blogs = await blogsService.getBlogs(req.query);
     return res.status(HTTP_STATUSES.OK).send(blogs);

4. SERVICE (blogs.services.ts)
   ────────────────────────────────────────────────────────────────────────
   Входные данные:
     query = {
       pageNumber: 1,           // уже число (преобразовано middleware)
       pageSize: 10,            // уже число
       searchNameTerm: "test"
     }
   
   Действия:
     - Применяет дефолтные значения (если нужно)
     - Преобразует SortDirection в MongoSortDirection
     - Вызывает репозиторий: blogsRepository.getBlogs({...})
     - Обрабатывает ошибки и бросает доменные исключения
   
   Код:
     const pageNumber = query.pageNumber || DEFAULT_PAGE;
     const sortDirection = query.sortDirection || DEFAULT_SORT_DIRECTION;
     
     return await blogsRepository.getBlogs({
       pageNumber,
       pageSize: query.pageSize || DEFAULT_PAGE_SIZE,
       sortBy: query.sortBy || "createdAt",
       sortDirection: toMongoSortDirection(sortDirection),
       searchNameTerm: query.searchNameTerm || "",
     });

5. REPOSITORY (blogs.repositories.ts)
   ────────────────────────────────────────────────────────────────────────
   Входные данные:
     params = {
       pageNumber: 1,
       pageSize: 10,
       sortBy: "createdAt",
       sortDirection: -1,        // преобразовано в число для MongoDB
       searchNameTerm: "test"
     }
   
   Действия:
     - Формирует MongoDB запрос с фильтрами
     - Выполняет запрос к БД: blogCollection.find(...)
     - Маппит документы БД в доменные модели (BlogItem)
     - Возвращает PaginatedResponse<BlogItem>
   
   Код:
     const filter: any = {};
     if (searchNameTerm) {
       filter.name = { $regex: searchNameTerm, $options: "i" };
     }
     
     const items = await blogCollection
       .find(filter)
       .sort({ [sortBy]: sortDirection })
       .skip(skip)
       .limit(pageSize)
       .toArray();
     
     return {
       items: items.map(mapDocumentToBlog),  // _id → id
       totalCount,
       pagesCount: Math.ceil(totalCount / pageSize),
       page: pageNumber,
       pageSize: pageSize,
     };

6. MONGODB
   ────────────────────────────────────────────────────────────────────────
   Выполняет запрос и возвращает документы с полем _id

7. ОБРАТНЫЙ ПОТОК
   ────────────────────────────────────────────────────────────────────────
   Repository → Service → Controller → HTTP Response
   
   Каждый слой возвращает данные в формате, понятном следующему слою:
   - Repository возвращает доменные модели (BlogItem[])
   - Service возвращает доменные модели или void
   - Controller формирует HTTP ответ

5. ПРАВИЛА: ЧТО КУДА КЛАСТЬ
================================================================================

5.1. КОНТРОЛЛЕР (Controller)
────────────────────────────────────────────────────────────────────────────
ЧТО КЛАСТЬ:
  ✓ Извлечение данных из req (params, query, body)
  ✓ Вызов сервисов
  ✓ Формирование HTTP ответов (res.status().send())
  ✓ Передача ошибок в next(error)

ЧТО НЕ КЛАСТЬ:
  ✗ Бизнес-логику (проверки, валидация бизнес-правил)
  ✗ Преобразование типов (Number(), String())
  ✗ Работу с БД
  ✗ Применение дефолтных значений
  ✗ Обработку ошибок (только next(error))

ПРИМЕР ПРАВИЛЬНОГО КОНТРОЛЛЕРА:
  getBlogById: async (req, res, next) => {
    try {
      const blog = await blogsService.getBlogById(req.params.id);
      return res.status(HTTP_STATUSES.OK).send(blog);
    } catch (error) {
      next(error);
    }
  }


5.2. СЕРВИС (Service)
────────────────────────────────────────────────────────────────────────────
ЧТО КЛАСТЬ:

  1. БИЗНЕС-ЛОГИКА И ВАЛИДАЦИЯ БИЗНЕС-ПРАВИЛ:
     ✓ Проверка существования сущностей (существует ли блог для поста)
     ✓ Валидация бизнес-правил (можно ли удалить блог с постами)
     ✓ Применение бизнес-ограничений (максимальное количество постов)
     ✓ Проверка прав доступа на уровне бизнес-логики
     ✓ Валидация состояний (можно ли обновить удалённый пост)

  2. ПРИМЕНЕНИЕ ДЕФОЛТНЫХ ЗНАЧЕНИЙ:
     ✓ pageNumber = 1, pageSize = 10 (если не указано)
     ✓ sortBy = "createdAt" (если не указано)
     ✓ Автоматическое заполнение полей (createdAt, isMembership)

  3. ПРЕОБРАЗОВАНИЕ ДАННЫХ:
     ✓ SortDirection ("asc"/"desc") → MongoSortDirection (1/-1)
     ✓ Преобразование форматов данных между слоями
     ✓ Нормализация входных данных

  4. ОБРАБОТКА ОШИБОК:
     ✓ Преобразование ошибок БД в доменные исключения
     ✓ Логирование ошибок для отладки
     ✓ Бросание правильных типов исключений (NotFoundError, ServiceError)

  5. КООРДИНАЦИЯ РЕПОЗИТОРИЕВ:
     ✓ Вызов нескольких репозиториев в правильном порядке
     ✓ Сборка данных из разных источников
     ✓ Пример: создание поста требует проверки существования блога

  6. ТРАНЗАКЦИИ И АТОМАРНЫЕ ОПЕРАЦИИ:
     ✓ Выполнение нескольких операций БД как единое целое
     ✓ Откат изменений при ошибке
     ✓ Пример: удаление блога + удаление всех его постов

  7. ВЫЧИСЛЕНИЯ И БИЗНЕС-РАСЧЁТЫ:
     ✓ Подсчёт статистики (количество постов в блоге)
     ✓ Расчёт агрегированных данных (средняя длина поста)
     ✓ Бизнес-метрики и аналитика

  8. АГРЕГАЦИЯ ДАННЫХ:
     ✓ Объединение данных из нескольких репозиториев
     ✓ Обогащение данных дополнительной информацией
     ✓ Пример: пост + информация о блоге + статистика

  9. КЭШИРОВАНИЕ (при необходимости):
     ✓ Кэширование часто запрашиваемых данных
     ✓ Инвалидация кэша при изменениях
     ✓ Оптимизация производительности

  10. ЛОГИРОВАНИЕ БИЗНЕС-СОБЫТИЙ:
      ✓ Логирование важных бизнес-операций
      ✓ Аудит изменений (кто, когда, что изменил)
      ✓ Отслеживание бизнес-метрик

  11. РАБОТА С ВНЕШНИМИ API И СЕРВИСАМИ:
      ✓ Интеграция с внешними сервисами (email, SMS, платежи)
      ✓ Вызов внешних API для получения данных
      ✓ Синхронизация с внешними системами

  12. УПРАВЛЕНИЕ ЖИЗНЕННЫМ ЦИКЛОМ СУЩНОСТЕЙ:
      ✓ Автоматические действия при создании/удалении
      ✓ Каскадные операции (удаление постов при удалении блога)
      ✓ Управление состояниями (активен/неактивен)

ЧТО НЕ КЛАСТЬ:
  ✗ HTTP операции (req, res, next)
  ✗ Прямую работу с БД (только через репозитории)
  ✗ Маппинг документов БД (это в репозитории)
  ✗ Валидацию формата данных (это в middleware/validations)
  ✗ Работу с файловой системой напрямую (лучше через утилиты)

ПРИМЕРЫ ПРАВИЛЬНОГО СЕРВИСА:

  Пример 1: Простая проверка существования
  ────────────────────────────────────────────────────────────────────────
  getBlogById: async (id: string): Promise<BlogItem> => {
    try {
      const blog = await blogsRepository.getBlogById(id);
      if (!blog) {
        throw new NotFoundError("Blog not found");
      }
      return blog;
    } catch (error) {
      if (error instanceof NotFoundError) {
        throw error;
      }
      throw new DatabaseError("Failed to get blog", error);
    }
  }

  Пример 2: Координация нескольких репозиториев
  ────────────────────────────────────────────────────────────────────────
  createPost: async (post: CreatePostDTO): Promise<PostItem> => {
    try {
      // Бизнес-правило: проверка существования блога
      const blog = await blogsRepository.getBlogById(post.blogId);
      if (!blog) {
        throw new NotFoundError("Blog not found", "blogId");
      }
      
      // Бизнес-правило: проверка лимита постов
      const postsCount = await postsRepository.countByBlogId(post.blogId);
      if (postsCount >= MAX_POSTS_PER_BLOG) {
        throw new ServiceError("Maximum posts limit reached");
      }
      
      return await postsRepository.createPost(post);
    } catch (error) {
      if (error instanceof NotFoundError || error instanceof ServiceError) {
        throw error;
      }
      throw new DatabaseError("Failed to create post", error);
    }
  }

  Пример 3: Транзакция (удаление блога с постами)
  ────────────────────────────────────────────────────────────────────────
  deleteBlog: async (id: string): Promise<boolean> => {
    try {
      // Проверка существования
      const blog = await blogsRepository.getBlogById(id);
      if (!blog) {
        throw new NotFoundError("Blog not found");
      }
      
      // Бизнес-правило: можно ли удалить блог с постами?
      const postsCount = await postsRepository.countByBlogId(id);
      if (postsCount > 0 && !blog.allowDeleteWithPosts) {
        throw new ServiceError("Cannot delete blog with posts");
      }
      
      // Транзакция: удаление постов + удаление блога
      await postsRepository.deleteAllByBlogId(id);
      return await blogsRepository.deleteBlog(id);
    } catch (error) {
      if (error instanceof NotFoundError || error instanceof ServiceError) {
        throw error;
      }
      throw new DatabaseError("Failed to delete blog", error);
    }
  }

  Пример 5: Вычисления и бизнес-расчёты
  ────────────────────────────────────────────────────────────────────────
  calculateBlogRating: async (id: string): Promise<number> => {
    try {
      const blog = await blogsRepository.getBlogById(id);
      if (!blog) {
        throw new NotFoundError("Blog not found");
      }
      
      const posts = await postsRepository.getPostsByBlogId(id, {});
      
      // Бизнес-расчёт: рейтинг на основе количества постов и их длины
      const totalLength = posts.items.reduce((sum, post) => 
        sum + post.content.length, 0
      );
      const avgLength = totalLength / posts.items.length;
      const rating = (posts.items.length * 10) + (avgLength / 100);
      
      return Math.round(rating * 100) / 100; // Округление до 2 знаков
    } catch (error) {
      if (error instanceof NotFoundError) {
        throw error;
      }
      throw new DatabaseError("Failed to calculate rating", error);
    }
  }

9.1. КОГДА НУЖЕН СЕРВИС, А КОГДА МОЖНО ОБОЙТИСЬ БЕЗ НЕГО
────────────────────────────────────────────────────────────────────────────

СЕРВИС НУЖЕН, ЕСЛИ:
  ✓ Есть бизнес-логика (проверки, правила, расчёты)
  ✓ Нужна координация нескольких репозиториев
  ✓ Требуется преобразование данных между слоями
  ✓ Нужны транзакции или атомарные операции
  ✓ Требуется агрегация данных из разных источников
  ✓ Есть интеграция с внешними сервисами
  ✓ Нужно логирование бизнес-событий

СЕРВИС МОЖЕТ БЫТЬ ПРОСТЫМ (тонкая прослойка), ЕСЛИ:
  - Просто передача данных от контроллера к репозиторию
  - Нет бизнес-логики
  - Нет координации репозиториев
  - Нет преобразований данных

ПРИМЕР ПРОСТОГО СЕРВИСА (тонкая прослойка):
  getBlogById: async (id: string): Promise<BlogItem | null> => {
    return await blogsRepository.getBlogById(id);
  }

ПРИМЕР СЛОЖНОГО СЕРВИСА (с бизнес-логикой):
  createPost: async (post: CreatePostDTO): Promise<PostItem> => {
    // Проверка существования блога (бизнес-правило)
    const blog = await blogsRepository.getBlogById(post.blogId);

    }
    
    // Создание поста
    return await postsRepository.createPost(post);
  }


9.2. ПАТТЕРНЫ РАБОТЫ С СЕРВИСАМИ
────────────────────────────────────────────────────────────────────────────

ПАТТЕРН 1: Service как Facade (Фасад)
  Сервис скрывает сложность работы с несколькими репозиториями
  Контроллер вызывает один метод сервиса, а сервис координирует работу
  
  Пример:
    // Контроллер
    const result = await blogsService.getBlogWithPosts(blogId);
    
    // Сервис координирует работу
    getBlogWithPosts: async (id: string) => {
      const blog = await blogsRepository.getBlogById(id);
      const posts = await postsRepository.getPostsByBlogId(id);
      return { blog, posts };
    }

ПАТТЕРН 2: Service как Validator (Валидатор бизнес-правил)
  Сервис проверяет бизнес-правила перед операциями
  
  Пример:
    deleteBlog: async (id: string) => {
      // Бизнес-правило: нельзя удалить блог с активными постами
      const hasActivePosts = await postsRepository.hasActivePosts(id);
      if (hasActivePosts) {
        throw new ServiceError("Cannot delete blog with active posts");
      }
      return await blogsRepository.deleteBlog(id);
    }

ПАТТЕРН 3: Service как Transformer (Преобразователь)
  Сервис преобразует данные между форматами
  
  Пример:
    getBlogs: async (query: GetBlogsQuery) => {
      // Преобразование SortDirection для MongoDB
      const mongoSort = toMongoSortDirection(query.sortDirection);
      return await blogsRepository.getBlogs({
        ...query,
        sortDirection: mongoSort,
      });
    }

ПАТТЕРН 4: Service как Orchestrator (Оркестратор)
  Сервис координирует сложные операции с несколькими шагами
  
  Пример:
    transferPosts: async (fromBlogId: string, toBlogId: string) => {
      // 1. Проверка существования блогов
      const fromBlog = await blogsRepository.getBlogById(fromBlogId);
      const toBlog = await blogsRepository.getBlogById(toBlogId);
      if (!fromBlog || !toBlog) {
        throw new NotFoundError("Blog not found");
      }
      
      // 2. Получение постов
      const posts = await postsRepository.getPostsByBlogId(fromBlogId);
      
      // 3. Обновление постов
      for (const post of posts.items) {
        await postsRepository.updatePost(post.id, {
          ...post,
          blogId: toBlogId,
          blogName: toBlog.name,
        });
      }
      
      return { transferred: posts.items.length };
    }


9.3. РАБОТА С ОШИБКАМИ В СЕРВИСАХ
────────────────────────────────────────────────────────────────────────────

ПРАВИЛО 1: Пробрасывание доменных исключений
  Сервис должен бросать доменные исключения (NotFoundError, ServiceError),
  а не технические (Error, DatabaseError из репозитория)
  
  Правильно:
    if (!blog) {
      throw new NotFoundError("Blog not found");
    }
  
  Неправильно:
    if (!blog) {
      throw new Error("Blog not found"); // Техническая ошибка
    }

ПРАВИЛО 2: Оборачивание ошибок репозитория
  Ошибки репозитория оборачиваются в ServiceError или DatabaseError
  
  Правильно:
    try {
      return await blogsRepository.getBlogById(id);
    } catch (error) {
      if (error instanceof NotFoundError) {
        throw error; // Пробрасываем доменную ошибку
      }
      throw new DatabaseError("Failed to get blog", error); // Оборачиваем техническую
    }

ПРАВИЛО 3: Логирование ошибок
  Сервис может логировать ошибки для отладки, но не должен обрабатывать их
  
  Пример:
    try {
      return await blogsRepository.getBlogById(id);
    } catch (error) {
      console.error("Service error in getBlogById:", error);
      throw new DatabaseError("Failed to get blog", error);
    }


9.4. ОПТИМИЗАЦИЯ СЕРВИСОВ
────────────────────────────────────────────────────────────────────────────

ОПТИМИЗАЦИЯ 1: Кэширование часто запрашиваемых данных
  Пример:
    getBlogById: async (id: string) => {
      // Проверка кэша
      const cached = cache.get(`blog:${id}`);
      if (cached) {
        return cached;
      }
      
      // Получение из БД
      const blog = await blogsRepository.getBlogById(id);
      if (blog) {
        cache.set(`blog:${id}`, blog, 3600); // Кэш на 1 час
      }
      return blog;
    }

ОПТИМИЗАЦИЯ 2: Batch операции (пакетные операции)
  Пример:
    getBlogsByIds: async (ids: string[]) => {
      // Вместо N запросов - один запрос
      return await blogsRepository.getBlogsByIds(ids);
    }

ОПТИМИЗАЦИЯ 3: Ленивая загрузка (lazy loading)
  Пример:
    getBlogWithPosts: async (id: string, includePosts: boolean = false) => {
      const blog = await blogsRepository.getBlogById(id);
      if (!blog) {
        throw new NotFoundError("Blog not found");
      }
      
      if (includePosts) {
        const posts = await postsRepository.getPostsByBlogId(id);
        return { ...blog, posts };
      }
      
      return blog;
    }


9.5. ТЕСТИРОВАНИЕ СЕРВИСОВ

Сервисы должны быть легко тестируемыми:
  - Зависимости (репозитории) передаются через параметры или DI
  - Нет прямых зависимостей от БД или HTTP
  - Бизнес-логика изолирована и может быть протестирована отдельно

Пример тестируемого сервиса:
  export const blogsService = {
    getBlogById: async (
      id: string,
      repository: BlogsRepository = blogsRepository // DI через параметр
    ): Promise<BlogItem> => {
      const blog = await repository.getBlogById(id);
      if (!blog) {
        throw new NotFoundError("Blog not found");
      }
      return blog;
    },
  };

  - SearchService: поиск по нескольким источникам


9.7. КОМПОЗИЦИЯ СЕРВИСОВ
────────────────────────────────────────────────────────────────────────────

Сервисы могут использовать другие сервисы:
  - PostService может использовать BlogService для проверки существования блога
  - AnalyticsService может использовать BlogService и PostService для сбора данных

Пример:
  // posts/services/posts.services.ts
  import { blogsService } from "../../blogs/services/blogs.services";
  
  createPost: async (post: CreatePostDTO) => {
    // Использование другого сервиса
    const blog = await blogsService.getBlogById(post.blogId);
    if (!blog) {
      throw new NotFoundError("Blog not found", "blogId");
    }
    return await postsRepository.createPost(post);
  }

ВАЖНО: Избегайте циклических зависимостей между сервисами!


9.8. РЕЗЮМЕ: ЧТО ДЕЛАЕТ СЕРВИС
────────────────────────────────────────────────────────────────────────────

Сервис - это слой бизнес-логики, который:

  ✓ Применяет бизнес-правила и валидирует их
  ✓ Координирует работу нескольких репозиториев
  ✓ Преобразует данные между форматами
  ✓ Выполняет вычисления и расчёты
  ✓ Агрегирует данные из разных источников
  ✓ Управляет транзакциями
  ✓ Интегрируется с внешними сервисами
  ✓ Логирует бизнес-события
  ✓ Обрабатывает ошибки и преобразует их в доменные исключения

  ✗ НЕ работает с HTTP (req, res)
  ✗ НЕ работает напрямую с БД (только через репозитории)
  ✗ НЕ маппит документы БД (это в репозитории)
